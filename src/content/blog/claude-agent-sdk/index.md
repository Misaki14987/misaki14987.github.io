# Claude Agent SDK

原文：[Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)

实际开发的时候我们可以用Claude Agent SDK而不是自己手写loop，减少部分繁杂的部分，牺牲一部分自由度。

Claude自己又把loop拓展了一下，变成了采集信息（context）-> 借用各种工具干活 -> 验证任务 然后循环起来

### Context（上下文）
- Agentic Search and FS：让模型自己探索文件系统，使用grep，tail这种东西看看文件，获取必要的环境信息，填充上下文
- Semantic Search（语义搜索）：可能像是RAG这种东西，把内容切块然后转成向量再检索。通常比Agentic Search更快，但准确率可能更低，更难维护，过程也不透明。A/建议先用Agentic Search，需要更快或者更多样的结果时再加语义搜索。不过我觉得这个结论主要要看场景而不是优先级，语义搜索不依赖关键词完全匹配，在大量自然语言文档中可能更好用。两种方式也可以结合，先用语义搜索找候选内容，再让Agent读取原文。
- SubAgent：把任务分派给其他的子Agent，好处有两个：一是可以并行，多个子Agent同时干不同的活；二是管理上下文，每个子Agent有自己独立的上下文窗口，干完只把有用的信息交回给主Agent，而不是把整个上下文都塞回去。这样主Agent的上下文管理比较干净，特别适合要翻大量信息、但大部分都没用的任务。另外，子Agent最好把找到的信息来源也带回来，而不是只返回总结，不然主Agent拿到一个结论而没办法判断这个结论有没有依据从而可能导致误判
- Compact：一个Agent的上下文快到窗口上限的时候，SDK会自动把之前的消息总结压缩一下，这样Agent就不会把上下文跑满。但压缩是有损的，不一定能保留所有关键信息。如果比如说重要的文件路径或者之前的错误原因被省略了就还要重新检索，另外Compact和Memory也不完全一样，Compact主要解决当前上下文空间不够的问题，Memory则是让Agent能够长期保存和重新获取信息，所以重要的业务状态最好保存在外部，而不是依赖模型记住。至于具体怎么压缩、保留哪些关键信息，吗的看过讲解又忘掉了，等学上下文工程的时候再细看
上面的概念我感觉还是需要细致的了解一下

### Action
- Tool Calling：工具调用，我们可以造一堆工具让AI使用。工具的定义会一直占着模型的上下文，而且模型做决定时会优先考虑这些工具，所以工具不是越多越好，应该只把Agent最主要、最常用的动作做成工具，这样也不用让AI一遍遍造轮子。另外工具设计上，工具设计不只是考虑能干什么，还要考虑返回什么，比如一个搜索工具一次返回几万行结果，Agent还是得从里面重新找有用的信息。最好能在工具层面就进行筛选，只返回必要的内容
- Bash / Script：使用Bash的命令行工具同样可以做到很多事情，比如grep获取文件的细节，sed修改文件等等，更复杂的问题可以编写py script来解决。哦我想到需要一个注意的地方就是我们通常需要限制命令行工具的输出，因为它们可能输出大量无用的内容占据上下文
- Code generation：这不是SDK的某个功能，而是一种设计思路：想想哪些任务可以用代码来表达。代码精确、可以组合、可以无限复用，很适合当Agent的输出。比如Claude.ai生成Excel、PPT、Word文件，靠的就是让Claude写Python脚本。就像是让agent操纵blender生成模型，也可以生成一堆代码，而不是通过视觉造模型。所以活用ai强大的代码功能
- MCP：mcp方便Agent连接外部系统，完成授权，api调用等工作，不用每次都自己开发一套API集成。认证、OAuth这些东西可以由具体的MCP Server封装

### Verify
- Define rules：最有效的反馈是给输出定好明确的规则，然后告诉模型哪些规则没通过、为什么没通过。我想到的是在AGENT.md中编写好代码后写测试来验证，这是比较简单的定义规则的方法，或者用code lint这种东西检查代码（当然AGENT.md是写好了Agent不一定遵守，最好强制性的比如放进CI里这种）。原文还提到生成TypeScript再lint，比直接生成JavaScript好，因为类型检查又多了一层反馈（所以2026年了还有人在写Pure JS吗？）
- Visual feedback：让有视觉能力的ai截图看看前端代码实现的具体的效果，或者用playwright这种调试浏览器看看
- LLM as Judge：让另外一个AI按一些模糊的规则来评判。相比让写代码的Agent自己检查，换一个新的AI会好一些，因为~~天天刷推~~看到大家说AI普遍会对自己完成的任务更加自信嗯。当然实际应用上这个方法本身不太稳，另一个AI也不一定就更客观，它同样可能犯错，还会带来很大的延迟和成本，只有在"效果能提升一点都值得"的场景才适合用

### Test and Improve
改进Agent最好的方法，是仔细看它的输出，尤其是失败的情况，然后站在它的角度想一想：它手上的工具够不够用？原文还给了几个自检问题：
- Agent误解了任务，它可能缺少关键信息，能否调整搜索 API 的结构，使其更容易找到所需了解的内容
- Agent反复在某一任务上失败，能否在工具调用中添加一条正式规则，以识别并修复该失败
- Agent无法修复其错误，能否为它提供更有用或更具创造性的工具，以便以不同的方式处理该问题
- Agent在添加功能时表现出现波动，能否基于客户使用情况构建一个具有代表性的测试集，用于程序化评估（或评估）
- 不能能只看Agent最后输出的文字，还得看任务是不是真的完成了，有没有调用错误的工具、产生不该有的副作用。否则它最后总结得再漂亮，也可能只是看起来完成了任务而已

## 12-Factor Agents · Factor 8：自己掌握控制流

原文:[Factor 8: Own your control flow](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-08-own-your-control-flow.md)

Factor 8讲的是自己掌握Agent的控制流。前面Claude Agent SDK已经帮我们封装了Loop，但并不是所有任务都适合让Agent一直循环执行下去。比如一个Agent准备部署后端服务，模型已经决定调用部署工具了，但是这种操作显然不能让它随便执行，最好先经过人工审批。这里就需要在**模型选择工具之后、真正执行工具之前**暂停Agent

这个时间点很关键，因为模型已经确定了要调用哪个工具、传入什么参数，但是操作还没有实际发生。我们可以先把调用请求保存下来，等用户批准之后再继续。

原文用一个简单的Loop举了几个例子：
- `request_clarification`：模型需要向用户询问更多信息，就先发送问题、保存状态，然后`break`退出Loop，等待用户回复。
- `fetch_open_issues`：模型需要查询Issue，直接执行工具，把结果加入上下文，然后`continue`进入下一轮。
- `create_issue`：创建Issue需要人工审批，就先申请审批、保存状态，再`break`，等收到外部事件之后恢复执行。

所以这里的`break`和`continue`并不是简单地根据模型有没有完成任务来决定，而是根据当前操作是否需要等待外部事件。、

简单理解的Agent Loop基本就是模型不断调用工具，直到它认为任务完成。如果真这么简单就太棒了哈哈，但这种写法有个问题，如果中途需要等人审批，或者等待某个耗时很长的任务完成，就不能一直这么循环下去

如果没有办法中断和恢复，通常只剩下三种选择：
1. 让程序一直运行，在内存里等待结果。但如果进程中途崩溃，就可能只能从头开始。
2. 限制Agent只能调用搜索、总结之类的低风险工具，不让它执行重要操作。
3. 直接给Agent更大的权限，指望它别搞出问题。

第三种显然有点赌狗，当然用人不疑疑人不用嘛（。所以自己掌握控制流的意义不只是能随便写`if/else`，而是可以根据业务需要暂停和恢复任务。不过我觉得这里还涉及一个问题：恢复的不只是模型上下文，还有程序的执行状态。比如Agent已经成功创建了Issue，但是程序在记录结果之前崩溃了。恢复之后如果重新执行创建操作，就可能出现两个重复的Issue。所以需要考虑怎么保存任务状态、记录哪些工具已经执行过，以及如何避免恢复时重复操作。这就涉及Durable Execution和幂等性，之后再研究研究
### 和Claude Agent SDK的取舍

回到开头，使用Claude Agent SDK确实可以省去自己实现Loop的麻烦，但如果业务需要复杂的人工审批、异步等待、故障恢复，单纯依赖SDK的默认执行流程可能还不够。

当然也不是说用了SDK就无法控制这些事情。Claude Agent SDK本身已经提供了Hooks、权限控制和Session Resume等机制，可以处理部分暂停和恢复的需求。只是Session能够恢复，不代表整个业务流程就能够安全恢复。比如工具调用已经产生了副作用，系统还得知道这个操作究竟有没有成功，不能恢复之后又执行一遍

所以我的想法是，普通的Agent可以优先使用SDK；如果需要复杂的业务控制流，可以考虑自己管理外层的执行状态，让SDK负责模型与工具的交互。只有现有机制确实满足不了需求的时候，再考虑自己实现Loop。毕竟自己写Loop也不只是一个`while True`，后面的上下文管理、错误处理、工具执行、日志这些东西也都得自己维护
